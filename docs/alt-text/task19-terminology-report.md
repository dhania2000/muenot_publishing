Implemented on `feat/phase3-task08-math-ocr`, 2026-10-28. Reuses the existing generation settings, governed image call, saved evidence, manual-edit endpoint, version history, Review inspector and document-output QA. No translation API, glossary database, guideline management screen, OCR engine or version table was added.

## Language and terminology policy
`literal-source.v1` records requested output language, selected subject/audience/grade, OCR modes actually supplied as evidence, document scripts, and distinct unknown/not-assessed states for source language, document language and reviewer-edited language. OCR recognition mode does not select the description language. Supported prose languages remain English and Devanagari Hindi; unsupported explicit language requests are rejected instead of silently changing the requested output into a default.

Built-in rules preserve original labels, case-sensitive scientific abbreviations, chemical/unit symbols, Greek letters, mathematical notation, subscripts/superscripts and proper names while adapting prose to the requested reader. They forbid silent label translation, Romanized Hindi, unsupported chart values/causal claims and exercise solving. OCR, LaTeX, presentation MathML and natural-language explanation remain distinct representations; syntax/rendering never proves source or scientific correctness.

The repository has no active client/project glossary, approved guideline registry or guideline parser. Generation therefore continues with safe platform defaults, `glossary: unavailable` and `guideline: null`. No supplied source/editor text can declare itself an approved glossary or override mandatory security/review. Client-supplied/cross-tenant guideline fields are rejected by the existing request boundary. Actual active-guideline ingestion, versioned terminology overrides and guideline-enabled tenant evaluation remain unavailable until a real authorized source is implemented; none is invented or required for normal generation.

## Read-only checks and Unicode
Deterministic review warnings cover invalid Unicode/replacement characters, obvious requested-prose script mismatch, missing printed units when their exact numeric token is used, changed verified-source notation and capitalization changes in supported case-sensitive technical tokens. Source constraints come only from reviewer-verified current corrections; raw recognition is not promoted to fact. Script checks and notation-equivalence checks are heuristic: technical Latin text can be valid in Hindi output and a spoken/linear math representation may be correct. No text is automatically translated, replaced, solved, corrected or approved.

Generation/editor-context truncation now uses the existing grapheme-safe bounder. Malformed UTF-16 in description fields, warnings and manual edits is rejected before persistence rather than silently replaced. Devanagari matras/conjuncts, nukta forms, numerals, mixed script and scientific symbols remain Unicode. Manual text uses the existing NFC normalization; canonical equivalents are not treated as a new translation. Technical text passes UTF-8 JSON and existing CSV export round trips, including BOM support.

The generation record snapshots the effective policy and actual issues in its existing audit JSON. Active generated content stores its actual selected output language; regenerating an approved asset still preserves the approved content/language. Explicit reviewer saves can retain the selected language through the existing optimistic edit service; the language choice and policy version are recorded in the edit note. Reviewer-edited prose language remains not assessed rather than being inferred as verified.

The short-alt target is an editorial preference throughout generation, manual editing and export QA. A necessary equation/label longer than the configured target may be saved intact with a warning, within the existing 1,000-character server safety cap. It is not automatically shortened or described as violating a universal WCAG limit. Existing document-output QA additionally checks supported source-unit/notation differences against the immutable approved text and uses rule version `task19.v1`; language-dependent checks run only when that language is actually available in the input. Native insertion/export behavior is unchanged.
